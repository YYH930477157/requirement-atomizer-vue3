# FAR 可达性前置分析（自动通过门是否会开）

> 起因：V4 改动评审报告 §三 高险第 3 条——`far = 1 - precision` 对微型真值集（100–200 条）
> 系统性偏高，真值标注后自动通过门（`far < 2%`）可能**永远不开**。本文是给真值标注阶段
> 的纯前置决策输入，不改任何代码；结论须在真值标注完成后用 `tools/functional_truth_eval.py`
> 实测复核。

## 1. 门禁现状（代码事实）

- 阈值：`adjudicate.py:63 DEFAULT_FAR_THRESHOLD = 0.02`（误受率 < 2% 才允许自动通过）。
- 计算：`adjudicate.py:481 far = 1.0 - precision`；`calibration_state()` 在
  `far < far_threshold()` 时返回 `calibrated`，否则 `insufficient`（line 482）。
- precision 口径：`tools/functional_truth_eval.py:160`
  `precision = matched_product_count / total_product`。
  - `total_product` = 该文档的功能需求产物总数（分母）。
  - `matched_product_count` = 锚点能回指到真值集的产物数；其余为 `floating_product`
    （漂浮产物，算作误受，进 far 分子）。
- 真值集：`adjudicate.py:124 truth_set_path()` 默认 `golden_sets/gold_functional_v1/truth.jsonl`；
  该文件**当前为空**（pending）→ `adjudicate.py:14` 自动通过硬禁用（reject/review 仍可用）。
- 版本：`adjudication-v2`。本文分析基于该版本的 precision/far 口径，若口径变更需重算。

## 2. 分母口径澄清（关键）

`far` 的分母是 **`total_product`（产物数 N）**，不是真值条目数 T。一条产物被判 floating
当且仅当它的锚点与**任意**真值锚点都不重叠（`evaluate_doc` line 144/152 的 `_anchor_overlap`）。

这意味着一条真值大致只能"接住"与它锚点重叠的产物。因此：

> **匹配产物数 ≤ 真值条目数**（每条真值至多稳定接住一组重叠产物），
> **漂浮产物数 ≥ N − T**。

## 3. 微型真值集下 far 系统性偏高（数学下界）

由第 2 节：

```
far = floating / N ≥ (N − T) / N
```

代入真实量级（产物数 N 取自实测：SBD 635 条功能需求，见 CLAUDE.md 质量门记录）：

| 真值集规模 T | far 下界 (N=635) | 距 2% 门 |
|---|---|---|
| 100 | (635−100)/635 = **84.3%** | 远超 |
| 150 | (635−150)/635 = **76.4%** | 远超 |
| 200 | (635−200)/635 = **68.5%** | 远超 |
| 600 | (635−600)/635 = 5.5% | 仍超 |
| 622 | (635−622)/635 = 2.0% | 卡门 |
| ≥ 623 | < 2% | 可达（需零漂浮） |

**结论 1**：对一份 635 产物的文档，微型真值集（100–200）下 `far` **数学下界即 68%–84%**，
2% 门**确定不可达**。这不是模型不够好，而是真值集只覆盖文档一小部分，导致大量**本应正确**
的产物因真值未覆盖而落为 floating、被错算成误受。

> 注：`tools/functional_truth_eval.py:12-13` 已明确"对微型/pending 真值集，precision 是下界
> （产物可能指向真值未覆盖的真实位置）"。far 是其镜像上界——偏高是口径后果，不是真实误受率。

## 4. 统计涨落（当真值集接近完整覆盖时）

只有当 T 接近 N（真值集近完整）时，far 才有机会落到 2% 附近，此时涨落由"少量漂浮"主导。
以小文档 N ≈ T ≈ 150 为例（简报点出的口径）：

| 漂浮数 | far (N=150) | 是否 < 2% |
|---|---|---|
| 0 | 0.00% | ✓（点估计） |
| 1 | 0.67% | ✓ |
| 2 | 1.33% | ✓ |
| 3 | 2.00% | ✗（卡门） |

即 **3 个漂浮就顶到 2% 门**。更严苛的是置信区间——即便观察到 0 漂浮，也无法统计上确认
真实 far < 2%：

- Rule of three：0 事件观察的 95% 上界 ≈ `3 / N`。
  - N = 150 → 上界 **2.0%**（恰好卡门，无法确认 < 2%）。
  - N = 300 → 上界 1.0%。
  - N = 500 → 上界 0.6%。

**结论 2**：即便零误受，要在统计上（95% CI 上界 < 2%）确认 far < 2%，需 **N ≥ 300 且 0 漂浮**；
容忍 1 个漂浮则需 N 更大（≈ 1 漂浮时 N ≥ 250 才让点估计 < 2%，但 CI 上界仍可能超）。
150 条规模的样本，统计涨落本身就与 2% 门同量级，**点估计通过也不稳**。

## 5. `<2%` 的可达条件（综合第 3、4 节）

同时满足：

1. **覆盖完整性**：真值集 T ≳ 0.98 × N（几乎逐条标注产物），否则 far 下界 > 2%。
2. **样本量**：N ≥ 300（让 95% CI 上界 ≤ 1%–2%，留出涨落余量）。
3. **匹配质量**：锚点回指零或近零漂浮（模型精度本身要过硬）。

对 SBD（635 产物）：需标注 ≈ 622+ 条真值，且 0–2 个漂浮，才可能过门。这与"微型真值集
100–200 条"的初始设想直接冲突——**微型真值集与 far <2% 门在数学上互斥**。

## 6. 备选裁决放量策略（若 far 门不可达）

评审原话："保守方向安全，但价值不到账"——门不开 = 自动通过不发生 = 自动化价值为零。
若不打算把真值集扩到近完整，应换一套放量策略，而不是死等 far：

- **A. 仅自动拒绝先上（推荐起步）**：误拒（false reject）可由人工恢复，误受（false accept）
  污染下游实现规格。先放量 `reject`（用 false-reject-rate 衡量，而非 far），`accept` 仍需人工。
  保守方向与现有"KB 只加分不否决/低分二分"纪律一致，且不依赖 far 可达。
- **B. 分级放量（按置信度分桶）**：把裁决建议按置信度分桶，先放高置信桶的 accept
  （高置信桶内 far 独立评估，更可能 <2%），低置信桶仍人工。代价：需为每桶单独标真值/算 far。
- **C. 分母口径修正（在覆盖子集内评估 far）**：把 far 分母从 `total_product` 收窄为
  "真值覆盖范围内的产物"（即 matched 候选集内再算误受），让微型真值集也能产出有意义的 far。
  代价：改变 `functional_truth_eval.py` precision 定义与 `adjudication-v2` 契约，属行为面变更，
  需 bump 版本并重冻结；且"覆盖范围外"的产物失去自动通过保护（需显式声明该范围不自动放）。
- **D. 扩大真值集到近完整**：唯一能让原 far 门自然开的路。对 SBD 需标 600+ 条，人工成本高；
  对多文档需逐文档标。若走此路，建议 N ≥ 300 的文档优先（涨落可控）。

## 7. 建议（给真值标注阶段）

1. **不要预期微型真值集（100–200）能开 far <2% 自动通过门**——第 3 节证明其数学下界 68%–84%。
2. 若目标是"自动通过开闸"：走 **D（近完整标注，T ≳ 0.98N，N ≥ 300）**；否则走 **A（仅自动拒绝先上）**，
   把 far 门降级为"自动 accept 的条件之一"而非唯一闸。
3. 真值标注完成后，**必须用 `tools/functional_truth_eval.py` 实测** `precision/far` 与 95% CI 上界，
   不可凭规模估算下结论（本文是前置分析，不是实测）。
4. 若选 C（口径修正），需在 `adjudication-v3` 明确"覆盖子集 far"的语义并重冻结契约，另起一份设计。
5. 当前 `truth.jsonl` 为空（pending）→ 自动通过硬禁用仍生效，无回归风险；本分析不影响现状。

## 8. 未决项

- 真值集的"一条真值接住几条产物"（1:1 还是 1:多）取决于 `_anchor_overlap` 粒度；第 3 节按
  保守的"≤ T"估算。若实际 1:多（一条真值接住多条同义产物），far 下界会更低，需实测修正。
- 多文档混合真值集时，`evaluate_doc` 按 doc_ref 分栏（line 181）；分母口径在跨文档聚合时
  需明确是 micro-average 还是 macro-average，本文按单文档 micro-average 分析。
